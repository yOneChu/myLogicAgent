## 1. 배경 및 필요성

### 1.1 현행 프로세스의 한계

수배로직에 따라 생성되는 BOM은 **본설계가 진행된 이후**에야 실물 검증이 이루어진다. 이 구조에서는 다음과 같은 문제가 발생한다.

- 하루에 설계완료된 다수의 호기 BOM을 사람이 수동으로 검증하는 데에는 한계가 있다.
- 로직 수정의 영향 범위가 즉시 확인되지 않아, 의도치 않은 자재 변경이 누적된 상태로 본설계에 반영된다.
- 자재 수량 이상이나 미수배 부품은 대부분 **설계 완료 이후 또는 출하 이후**에 발견된다.
- 발견 시점이 늦을수록 대응 비용이 커진다. 설계 단계의 수정은 로직 한 줄이면 끝나지만, 출하 이후에는 현장 대응·재수배·납기 지연으로 이어진다.

### 1.2 개선 방향

본설계 착수 전에 **대표호기의 BOM 구조를 사전 검증**하여, 로직 변경이 BOM에 미치는 영향을 매일 단위로 가시화한다. 사람이 주기적으로 확인하는 방식은 지속성이 없으므로, 수집·비교·판정 전 과정을 자동화한다.

## 2. 목적 및 목표

| 구분 | 내용 |
|---|---|
| 목적 | 본설계 착수 전 대표호기 BOM 구조의 사전 검증 체계 확립 |
| 정량 목표 | 브랜드별 대표호기 BOM을 1일 1회 자동 수집·비교, 전일 대비 변경분 100% 검출 |
| 정성 목표 | 변경 원인(로직 개정 / 비의도 변경)의 구분 가능, 미수배 부품의 조기 인지 |
| 최종 지향점 | 설계 완료 및 출하 이후 발생하던 BOM 기인 문제를 설계 이전 단계로 이관 |

---

## 3. 적용 범위

- **대상**: 최초설계BOM, 각 브랜드별로 선정한 대표호기
- **방식**: 대표호기의 **테스트버전(Test Version)** 을 별도 생성하여 운영. 실제 수주 호기가 아닌 검증 전용 버전을 사용하므로 실 업무 데이터에 영향을 주지 않는다.
- **주기**: 매일 1회 (일 배치)
- **제외**: 개별 수주 호기의 BOM 검증은 본 범위에 포함하지 않는다. (향후 확장 과제 — 9장 참조)

> **확정 필요**: 브랜드별 대표호기 선정 목록 및 선정 기준, 배치 실행 시각

## 4. 시스템 구성

### 4.1 아키텍처 개요

```
[PLM / 수배 시스템]
        │  ① BOM 추출 API 호출 (일 1회, 스케줄러)
        ▼
[Spring Boot 서버]
   ├─ 수집 모듈    : 대표호기 테스트버전 BOM 조회
   ├─ 저장 모듈    : 일자별 BOM 스냅샷 적재
   ├─ 비교 모듈    : 금일 스냅샷 ↔ 전일 스냅샷 Diff
   ├─ 판정 모듈    : 변경 유형 분류 및 등급 판정
   └─ 조회 API     : 화면/리포트용 조회 기능
        │
        ▼
[DB] 스냅샷 · Diff 결과 이력
        │
        ▼
[조회 화면] 일자별 변경 내역, 자재별 이력, 미수배 목록
```

### 4.2 기술 구성

| 구분 | 내용 |
|---|---|
| 서버 | Spring Boot (신규 구축) |
| 데이터 수집 | 기 개발 완료된 BOM 추출 API 활용 |
| 저장소 | 관계형 DB — 일자별 스냅샷 및 Diff 결과 이력 관리 |
| 실행 방식 | 스케줄러 기반 일 배치 자동 실행 + 수동 실행 지원 |
| 사용자 인터페이스 | 웹 조회 화면 (기 개발된 UI 활용/확장) |

## 5. 주요 기능

### 5.1 일일 BOM 스냅샷 저장

- 브랜드별 대표호기 테스트버전의 BOM을 매일 자동 수집하여 **일자 단위 스냅샷**으로 저장한다.
- 덮어쓰기가 아닌 **누적 저장** 방식으로, 임의 시점 간 비교와 변경 이력 추적이 가능하다.
- 수집 실패 시 재시도 및 실패 이력을 남긴다.

### 5.2 전일 대비 BOM 비교 (Diff)

금일 BOM과 전일 BOM을 비교하여 다음을 검출한다.

| 검출 유형 | 판정 내용 |
|---|---|
| 자재 추가 (Added) | 전일에 없던 자재가 신규 반영됨 |
| 자재 삭제 (Deleted) | 전일에 있던 자재가 누락됨 |
| 수량 변경 (Modified) | 동일 자재의 소요 수량이 변경됨 |
| 미수배 (Not Allocated) | BOM 상 필요하나 수배되지 않은 부품 |
| 변경 없음 (Unchanged) | 전일과 동일 |

### 5.3 변경 원인 판정

단순 검출에 그치지 않고, 검출된 변경이 **의도된 변경인지 여부**를 판단할 수 있도록 근거 정보를 함께 제공한다.

| 확인 항목 | 판단 관점 |
|---|---|
| 자재 변경 | 우리가 작성·개정한 수배로직에 의한 변경인가, 아니면 원인 불명의 변경인가 |
| 수량 급변 | 어떤 로직 조건 또는 데이터 변경이 수량 변동을 유발했는가 |
| 미수배 | 로직 미작성인가, 조건 불일치인가, 자재 마스터 문제인가 |

> **확정 필요**: 변경 원인을 자동 추적하려면 BOM 라인과 로직 PID의 연계 키가 필요하다. 현재 BOM 추출 데이터에 해당 정보가 포함되는지 확인 후, 미포함 시 1차는 담당자 수동 판정 → 2차에서 자동 연계로 고도화한다.

### 5.4 판정 등급 및 알림

| 등급 | 기준(안) | 조치 |
|---|---|---|
| 정상 | 변경 없음, 또는 개정 로직에 의한 설명 가능한 변경 | 이력만 기록 |
| 경고 | 수량 변경 등 확인이 필요한 변경 | 담당자 확인 |
| 오류 | 미수배 부품 발생, 자재 삭제 등 | 즉시 원인 파악 |

> **확정 필요**: 등급 판정의 구체적 임계 기준(예: 수량 변동률), 알림 수단 및 수신 대상

### 5.5 조회 기능

- 일자별 변경 요약 (브랜드/호기 단위 건수, 등급별 집계)
- 변경 상세 목록 (자재코드, 자재명, 전일 값, 금일 값, 변경 유형)
- 자재별 변경 이력 추적
- 미수배 부품 목록 및 지속 일수
- 임의 두 시점 간 비교

## 6. 데이터 설계 (안)

| 테이블 | 역할 | 주요 항목 |
|---|---|---|
| 대표호기 마스터 | 검증 대상 관리 | 브랜드, 호기 ID, 테스트버전 ID, 사용 여부 |
| BOM 스냅샷 헤더 | 수집 단위 관리 | 스냅샷 ID, 대상 호기, 수집일자, 수집 상태 |
| BOM 스냅샷 라인 | BOM 원본 보존 | 스냅샷 ID, 자재코드, 수량, 수배 상태, 레벨/부모 |
| Diff 결과 | 비교 결과 이력 | 비교일자, 기준/대상 스냅샷, 자재코드, 변경 유형, 전/후 값, 판정 등급 |
| 확인 이력 | 담당자 조치 기록 | Diff ID, 확인자, 확인일시, 원인 구분, 비고 |

「확인 이력」 테이블은 검출된 변경에 대해 담당자가 판단한 결과를 남기는 용도로, 반복되는 오탐을 걸러내고 판정 규칙을 개선하는 근거가 된다.

## 7. 기대효과

### 7.1 직접 효과

| 구분 | 개선 전 | 개선 후 |
|---|---|---|
| 변경 인지 시점 | 본설계 이후 또는 출하 이후 | 변경 발생 익일 |
| 변경 확인 방식 | 담당자 수작업 확인, 누락 가능 | 전 자재 자동 비교 |
| 미수배 발견 | 수배 단계 또는 현장 | 설계 착수 전 |
| 변경 근거 | 기억·개인 기록에 의존 | 일자별 이력으로 보존 |

### 7.2 파급 효과

- **품질**: 설계 BOM 오류의 사전 차단 → 출하 후 현장 문제 감소
- **비용**: 후행 단계에서 발생하는 재작업·재수배·현장 대응 비용 절감
- **로직 신뢰도**: 로직 개정의 영향 범위가 즉시 확인되므로, 개정에 따른 리스크를 정량적으로 관리 가능
- **자산화**: 일자별 BOM 이력이 축적되어 향후 AI 기반 이상 탐지·원인 분석의 학습 데이터로 활용 가능

## 9. 검토 필요사항 및 향후 과제

### 9.1 사전 확정 사항

1. 브랜드별 대표호기 선정 목록 — 몇 개 브랜드, 브랜드당 몇 호기를 대상으로 할 것인가
2. 테스트버전의 생성·갱신 주체 및 주기 — 테스트버전 자체가 오래되면 검증 의미가 약해진다
3. 스냅샷 데이터 보존 기간 및 예상 데이터 증가량
4. 판정 등급 임계 기준 및 알림 대상

### 9.2 예상 리스크

| 리스크 | 대응 방안 |
|---|---|
| 정상 변경까지 다량 검출되어 확인 피로 발생 | 확인 이력 기반으로 판정 규칙 점진 보정, 등급별 필터 제공 |
| PLM 데이터 변경으로 수집 실패 | 수집 실패 감지 및 알림, 재시도 로직 |
| 대표호기가 실제 수주 사양을 대표하지 못함 | 선정 기준 주기적 재검토 |

### 9.3 확장 과제

- 대표호기 외 실 수주 호기로의 검증 대상 확대
- 변경 원인의 로직 PID 자동 연계 및 ECO 이력 연동
- 축적된 이력 데이터를 활용한 AI 기반 이상 변경 탐지

## 10. 결론

본 과제는 "BOM을 매일 저장하고 어제와 비교한다"는 단순한 원리에 기반하지만, 검증 시점을 **본설계 이후에서 이전으로 이동**시킨다는 점에서 의미를 갖는다. 변경은 어차피 발생하며, 문제는 그것을 **언제 아는가**이다. 하루 단위로 알게 되면 로직 수정으로 해결되지만, 출하 후에 알게 되면 현장 대응이 된다. 본 시스템은 그 시점 차이를 만들어내는 것을 목표로 한다.
